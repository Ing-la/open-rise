## 一、前置准备：安装 GitHub CLI

### 1.1 检查是否已安装

```bash
gh --version
```

如果输出 `command not found` 则未安装。

### 1.2 安装方法

**Windows（winget）：**

```bash
winget install GitHub.cli
```

**macOS（Homebrew）：**

```bash
brew install gh
```

**Linux（apt）：**

```bash
sudo apt install gh
```

### 1.3 登录认证

```bash
gh auth login
```

根据提示选择：
1. 登录方式：选 **GitHub.com**
2. 认证方式：选 **Login with a web browser**
3. 浏览器中复制 one-time code 完成授权

**验证登录：**

```bash
gh auth status
# → ✓ Logged in to github.com as <your-username>
```

> 需要仓库的 push 权限。如果 token 有效期过期，`gh release create` 会报 401 错误，重新 `gh auth login` 即可。

## 二、GitHub Release CLI 理论

### 2.1 什么是 GitHub Release

GitHub Release 是基于 Git tag 的「发布快照」。每个 Release 关联一个 tag，附带：

- **标题**（Title）：人类可读的版本名
- **发布说明**（Release Notes）：Markdown 正文，描述本次变更
- **附件**（Assets）：二进制文件（exe、dmg、zip 等），用户直接从 Release 页面下载

Release 不是 Git 原生概念——底层只是一个 tag + GitHub 附带的元数据。没有 GitHub 也可以 git tag，但 Release 提供了分发入口。

> **重要认知：Release 和仓库代码是两套独立的内容。** Release 页面本质是一个文件存储 + 下载入口，上传的 exe 安装包不需要跟仓库代码有任何关系。哪怕仓库是空的，只要有权限就能上传文件。但安装包实际是项目代码构建出来的，所以流程上仍然是：本地代码 → 构建 → 上传到 Release。

### 2.2 `gh release create` 完整命令

```bash
gh release create <tag> \
  --title "<标题>" \
  --notes "<正文>" \
  [--notes-file <文件>] \
  [--prerelease] \
  [--draft] \
  <assets...>
```

**参数详解：**

| 参数 | 作用 | 示例 |
|------|------|------|
| `<tag>` | 创建的 Git tag 名，必须遵守 semver | `v0.1.0` |
| `--title` | Release 页面显示的大标题 | `"OpenRise v0.1.0"` |
| `--notes` | 直接写发布说明（适合短内容） | `"首次发布"` |
| `--notes-file` | 从文件读发布说明（适合长内容） | `./CHANGELOG.md` |
| `--prerelease` | 标记为预发布版，不推送给"稳定版"用户 | |
| `--draft` | 草稿模式，只你可见，确认无误后手动发布 | |
| `<assets>` | 要上传的文件，支持 glob 通配 | `./dist/*.exe` |

### 2.3 执行流程

```
git tag v0.1.0  ──────┐
                       │
gh release create v0.1.0 ───→ 1. 创建 tag（如果还没推）
                               2. 上传 assets
                               3. 生成 Release 页面
                               4. 可选：自动发布到 GitHub 仓库首页
```

⚠️ **重要行为**：`gh release create` 会在本地创建 tag 并推送到远程。如果本地 tag 已存在，会报错。需要覆盖时用 `--force`。

### 2.4 查看和管理 Release

```bash
# 查看所有 Release
gh release list

# 查看某个 Release 详情
gh release view v0.1.0

# 删除 Release（tag 会保留，需要额外删除）
gh release delete v0.1.0

# 修改 Release 信息
gh release edit v0.1.0 --title "新标题"

# 下载 Release 中的某个 asset
gh release download v0.1.0 -p "*.exe"
```

## 三、语义化版本（SemVer）

### 3.1 格式

```
v主版本.次版本.补丁
```

| 分段 | 递增时机 | 示例 |
|------|----------|------|
| **主版本** | 不兼容的 API 改动 | 1.0.0 → 2.0.0 |
| **次版本** | 向下兼容的功能新增 | 1.0.0 → 1.1.0 |
| **补丁** | 向下兼容的问题修复 | 1.0.0 → 1.0.1 |

### 3.2 V1 前（0.x）

`0.x` 阶段不受 SemVer 约束。`0.1.0` → `0.2.0` 可以包含任意变更，用户预期就是不稳定的。当前版本 `0.1.0` 正是此阶段。

### 3.3 预发布标签

```
v1.0.0-alpha.1
v1.0.0-beta.1
v1.0.0-rc.1
```

`--prerelease` 标记的 Release 不会出现在"Latest Release"中，适合发给测试用户。

## 四、构建产物与发布资产

### 4.1 当前构建流程

```
npm run build
  ├── prebuild: prisma migrate diff ... > prisma/schema.sql  ← 生成建表 SQL
  ├── next build: 静态导出到 out/                              ← 前端页面
  └── electron-builder: 打包整个应用                            ← 安装包
```

### 4.2 electron-builder 打包什么

electron-builder 默认行为：

1. 将 `main.js` 所在的整个目录（即整个项目根目录）扫描
2. 排除 `.gitignore` 中列出的文件
3. `package.json` 中的 `dependencies`（不是 devDependencies）会打包进去
4. Electron 二进制 + 你的代码 → 输出 `dist/` 目录下的安装包

当前配置（`electron-builder.yml`）已显式声明 `prisma/schema.sql` 在 `files` 中，确保被包含。

### 4.3 跨平台产物

| 平台 | 预期产物 | electron-builder 输出 |
|------|----------|-----------------------|
| Windows | `OpenRise Setup 0.1.0.exe` | `.exe`（NSIS 安装包） |
| macOS | `OpenRise-0.1.0.dmg` | `.dmg`（磁盘映像） |
| Linux | `OpenRise-0.1.0.AppImage` | `.AppImage`（便携应用） |

> **关键限制：不能跨平台打包。** electron-builder 调用的是当前操作系统的原生打包工具链（Windows 上的 signtool、macOS 上的 codesign），因此：
> - Windows 上跑 `npm run build` 只能产 `.exe`
> - macOS 上跑才能产 `.dmg`
> - Linux 上跑才能产 `.AppImage`
>
> 要一次拿到三个平台的安装包，需要走 CI/CD 自动打包（见下文）。

### 4.4 覆盖安装与数据安全

Windows NSIS 安装包默认覆盖安装到同一目录，用户数据不受影响：
- **程序文件**：`C:\Users\<用户名>\AppData\Local\Programs\OpenRise\`（新版覆盖旧版）
- **用户数据**：`C:\Users\<用户名>\AppData\Roaming\OpenRise\openrise.db`（安装包不动）

> NSIS 默认不自动卸载旧版，直接覆盖可能残留旧文件。有真实用户后再配 `guid` 和卸载检测即可。

## 五、发布流程

### 5.1 日常开发与发版的关系

```
日常提交：git add → git commit → git push
                                  ↓
                          仅更新代码，不影响 Release

发版提交：git tag v0.2.0 → git push --tags
                                  ↓
                        （可选）触发 CI/CD 自动打包
                          或本地手动 build → gh release create
```

两条线互不影响。日常可以频繁推送代码，只有打了 `v*` 的 tag 才和 Release 相关。

### 5.2 本地手动发布（当前做法）

```bash
# 1. 更新版本号（package.json 中的 version 字段）
# 2. 更新 CHANGELOG.md
# 3. 构建（用本地代码，跟远程仓库无关）
npm run build
# 4. 创建 GitHub Release
gh release create v0.1.0 \
  --title "OpenRise v0.1.0" \
  --notes-file CHANGELOG.md \
  "./dist/OpenRise Setup 0.1.0.exe"
```

> **不强制提交代码。** 构建和上传都基于本地文件，跟远程仓库代码状态无关。但建议发版前提交并推送一次，让 tag 指向对应的提交，方便以后回溯——用户拿着 v0.1.0 报 bug 时能精确定位到是哪份代码。

**局限**：只能在当前平台打一个平台的包。需要其他平台的安装包就得换机器手动跑。

### 5.3 CI/CD 自动发布（已配置，以后发版只需打 tag）

`.github/workflows/release.yml` 已就绪。推送 `v*` tag 后：

1. 先创建 Release 页面
2. 三平台并行构建（Windows/macOS/Linux）
3. 各自上传安装包到同一个 Release

以后发版只需一步：

```bash
git tag v0.2.0 && git push --tags
```

GitHub 会自动完成全部打包和上传，不需要本地跑 `npm run build`。

> ⚠️ **关于产物大小**：`next` 已移到 devDependencies，`electron-builder.yml` 已排除 `.next/` 目录。重新打包后预期从 **583MB → ~200MB**。

### 5.4 发布后验证

1. 从 GitHub Release 页面下载安装包
2. 安装到没有开发环境的机器
3. 首次启动确认自动建表无报错
4. 测试核心流程：创建 Brain → 创建 Role → Chat 对话 → Agent 任务 → Debate 辩论

## 六、常见问题

### Q: `gh release create` 和 `git tag && git push && gh release create` 的区别？

`gh release create <tag>` **一步完成**：创建 tag、推送到 remote、创建 Release、上传 assets。单独 `git tag` + `git push` 只推送 tag，不创建 Release 页面。

### Q: Release 和仓库代码有关系吗？

没关系。Release 本质是一个文件存储 + 下载页面，上传的 exe 不需要跟仓库代码有关联。但安装包本身是代码构建出来的，所以实践中是先有代码提交，再构建，再上传。

### Q: 上传失败的 assets 可以追加吗？

可以。`gh release upload <tag> <files...>` 向已存在的 Release 追加附件。

### Q: Windows 上能打 macOS 的包吗？

不能。需要对应平台的原生工具链。要一次拿三个平台的包请配 CI/CD（见 5.2 节）。

### Q: 发布后发现严重 bug 怎么办？

SemVer 流程：修复后 bump patch 版本，发布 `v0.1.1`。Release 页面会显示为"Latest Release"，用户重新下载即可。旧版本保留在 Release 列表中供回滚。

### Q: `--draft` 和 `--prerelease` 的区别？

| 模式 | 谁可见 | 用途 |
|------|--------|------|
| `--draft` | 仅仓库管理员 | 发布前的最终检查 |
| `--prerelease` | 所有人 | 测试版、预览版，不标记为 Latest |

可以先 `--draft` 检查，确认后再手动取消草稿发布。
