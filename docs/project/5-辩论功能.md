# 辩论赛功能（Debate）

## 产品定位

一个 LLM 编排的辩论赛沙盒。选 8 个辩手 + 1 个裁判（每个位置绑定一个角色/大脑），输入辩题和背景，系统按辩论赛规则依次驱动各位置发言，最终由裁判打分判定胜负。

**本质是 LLM 编排，不是 Agent** — 没有工具调用，没有 ReAct 循环。只是按规则依次调 LLM，喂入全部上下文，输出当前环节的发言。比 Agent 简单一个量级。

---

## 辩论流程

采用标准辩论赛格式，分为五个阶段：

```
Round 1 ─ 立论陈词（总预算 700 tokens ≈ 3'30"）
  正方一辩 → 反方一辩
  system prompt 提示 600~700 tokens 区间
  max_tokens=780 兜底（预算+80 余量）

Round 2 ─ 驳论阶段（总预算 400 tokens ≈ 2'00"）
  反方二辩 → 正方二辩
  system prompt 提示 300~400 tokens 区间
  max_tokens=480 兜底（预算+80 余量）

Round 3 ─ 对辩阶段（多轮交锋）
  正方三辩 ↔ 反方三辩 交替
  每方总预算: 400 tokens（对应 1'30"）
  system prompt 建议单次不超过 80 tokens（不强制）
  暴露剩余配额，max_tokens=剩余+80（防边界卡死）
  一方耗尽 → 对方继续直到自己也耗尽 → 双方都耗尽结束

Round 4 ─ 自由辩论
  正方先，双方交替
  每次从该方 4 人中加权随机选（三辩 50%）
  每方总预算: 1600 tokens（对应 4'00"）
  system prompt 建议单次不超过 80 tokens（不强制）
  暴露剩余配额，max_tokens=剩余+80（防边界卡死）
  一方耗尽 → 对方继续直到自己也耗尽 → 双方都耗尽结束

Round 5 ─ 总结陈词（总预算 700 tokens ≈ 3'30"）
  反方四辩 → 正方四辩
  system prompt 提示 600~700 tokens 区间
  max_tokens=780 兜底（预算+80 余量）

裁判评判
  喂入整场辩论记录
  输出：各辩手分数 + 胜负判定 + 最佳辩手 + 总结
```

### 对辩阶段的 token 计时机制

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `CROSS_TOKENS_PER_SIDE` | 400 | 每方可用 token 预算（约 1'30"），耗尽判定阈值 |
| `CROSS_MAX_TOKENS_BUFFER` | 80 | max_tokens 余量，防止边界卡死 |

逻辑：

```
正方三辩先发言，然后反方三辩，交替进行
每次 API 调用 max_tokens = 该方剩余配额 + CROSS_MAX_TOKENS_BUFFER（防边界卡死）
每方累计消耗 token = Σ 该方每次发言的 completion_tokens
当一方累计 token ≥ CROSS_TOKENS_PER_SIDE (400) → 该方时间用完，失去发言权
对方继续使用剩余 token 输出，直到自己也耗尽 → 双方都耗尽，对辩结束
```

max_tokens 多加 80 是为了防止配额将尽时 LLM 只剩 1~2 token 输出空间，既无法成句也无法触发耗尽判定。有了余量，最后一次发言自然会 overshoot 到 400+，干净利落地结束该方发言权。

### 自由辩论的 token 计时机制

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `FREE_DEBATE_TOKENS_PER_SIDE` | 1600 | 每方可用 token 预算（约 4'00"），耗尽判定阈值 |
| `FREE_DEBATE_MAX_TOKENS_BUFFER` | 80 | max_tokens 余量，防止边界卡死 |

逻辑：

```
正方先开始第一轮，之后交替发言
轮到某方时，从该方 4 人中加权随机选 1 人发言
  三辩权重 50%，其余 3 人平分剩余 50%（各 ~16.7%）
每次 API 调用 max_tokens = 该方剩余配额 + FREE_DEBATE_MAX_TOKENS_BUFFER（80）
每方累计消耗 token = Σ 该方每次发言的 completion_tokens
当一方累计 token ≥ FREE_DEBATE_TOKENS_PER_SIDE (1600) → 该方时间用完，失去发言权
对方继续使用剩余 token 输出，直到自己也耗尽
双方都耗尽 → 自由辩论结束
```

## 存储方案

采用 **SQLite/Prisma** 存储全部辩论数据，不使用 Markdown 或 JSONL。

| 方案 | 为什么不行 |
|------|-----------|
| Markdown 归档 | Chat/Agent 的记忆压缩用 Markdown/JSONL 是因为它们**归档后不再需要查询**。辩论赛数据需要被搜索（按辩题、角色、时间）、回放、统计，文件没有查询能力 |
| JSONL | 同上，不支持关系查询和联表 |

辩论赛的场景就是关系型擅长的：按辩题搜索、按角色筛选、按时间排序。

## 数据模型

### 表结构

```prisma
model Debate {
  id          String   @id @default(uuid())
  proTopic    String   // 正方辩题
  conTopic    String   // 反方辩题
  background  String?  // 背景资料
  summary     String?  // 辩论结束后由裁判 LLM 输出自动生成的摘要，供搜索工具快速返回
  status      String   @default("ongoing") // ongoing | completed
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  positions   DebatePosition[]
  messages    DebateMessage[]
  scores      DebateScore[]
  result      DebateResult?
}

model DebatePosition {
  id        String @id @default(uuid())
  debateId  String
  roleId    String // FK → Role.id，每个辩位绑定一个角色
  side      String // "pro" | "con" | "judge"
  position  Int    // 1-4（judge 为 0）
  brainId   String // FK → Brain.id，冗余存储方便查询

  debate    Debate @relation(fields: [debateId], references: [id], onDelete: Cascade)

  @@index([roleId])  // 快速查询"某角色参加过哪些辩论"
}

model DebateMessage {
  id          String   @id @default(uuid())
  debateId    String
  roleId      String   // FK → Role.id，发言者
  side        String   // "pro" | "con" | "judge"
  position    Int      // 1-4（judge 为 0）
  round       String   // "opening" | "rebuttal" | "cross" | "free" | "closing" | "judging"
  content     String   // 发言内容
  tokenCount  Int?     // 该发言消耗的 token 数
  roundIndex  Int      // 全场第几轮发言
  createdAt   DateTime @default(now())

  debate      Debate   @relation(fields: [debateId], references: [id], onDelete: Cascade)

  @@index([debateId, createdAt])  // 按时间顺序加载完整辩论
}
```
model DebateScore {
  id              String   @id @default(uuid())
  debateId        String
  roleId          String   // FK → Role.id
  side            String   // "pro" | "con"
  position        Int      // 1-4
  scoreContent    Int?     // 内容/论据 (30%)
  scoreLogic      Int?     // 逻辑/推理 (25%)
  scoreExpression Int?     // 表达/语言 (20%)
  scoreRebuttal   Int?     // 反驳/应变 (25%)
  totalScore      Float?   // 加权总分
  judgeComment    String?  // 裁判评语
  createdAt       DateTime @default(now())

  debate          Debate   @relation(fields: [debateId], references: [id], onDelete: Cascade)

  @@index([debateId])
}

// DebateResult — 辩论结果
model DebateResult {
  id              String   @id @default(uuid())
  debateId        String
  winner          String   // "pro" | "con"
  bestPro         Int?     // 正方最佳辩手 position
  bestCon         Int?     // 反方最佳辩手 position
  overallBest     Int?     // 全场最佳辩手 position
  bestSide        String?  // "pro" | "con"
  judgeSummary    String?  // 裁判总结
  createdAt       DateTime @default(now())

  debate          Debate   @relation(fields: [debateId], references: [id], onDelete: Cascade)
}
```

## 记忆架构（三层独立）

整个应用中存在三套独立的记忆体系，各不混淆：

| 记忆体系 | 存储方式 | 查询能力 | 谁在用 |
|---------|---------|---------|--------|
| **Chat 记忆** | Role.summary 压缩摘要 | 纯文本拼接进 system prompt | Chat 对话流 |
| **Agent 记忆** | .jsonl 归档 + DB | 按 session 独立管理，压缩后归档 | Agent 工具调用 |
| **辩论记忆** | Debate 表系（SQLite） | 全文搜索 + 角色/时间筛选 | **Chat** 通过 `search_debate_memory` 工具调用访问 |

### 辩论记忆的访问方式（Chat 工具调用）

Chat 现有的纯文本流 (`user → LLM → text`) 需要引入一次性的 tool_use 能力来支持辩论记忆查询：

```
用户提到"上次关于AI的辩论" →
    ↓
LLM 发起 search_debate_memory 工具调用 →
    ↓
Chat handler 检测到 tool_calls →
    ↓
查询 Prisma（按 topic/roleId 搜索 Debate + DebateResult） →
    ↓
回填搜索结果 → LLM 继续生成回复
```

这个改动是非侵入式的——只在绑定了参与过辩论的角色的 Chat 中，有条件地注册 `search_debate_memory` 工具。没有辩论历史的角色不受影响，Chat 保持原有行为。

### 搜索工具返回格式（建议）

```
工具名: search_debate_memory
参数: { query: string, roleId?: string }
返回:
{
  debates: [{
    id, topic, date, winner,
    myPosition: "正方二辩",
    opponent: "反方",
    summary: "裁判总结摘要..."
  }]
}
```

## 内置提示词系统

### 设计原则

**阶段提示词只做两件事**：告诉 LLM 当前是什么环节、目标是帮团队赢下比赛。不给结构要求、不给写作建议、不限制篇幅。角色的灵魂和性格由 soul+rule 决定，环节信息只负责让 LLM 知道「该说什么环节的话」。

**对辩和自由辩论暴露双方剩余 token 配额**，让 LLM 自己战略决策用多少——打猛了后面没弹药，省着了这轮没力度。甚至可以选择在对方耗尽后连续输出扩大优势。各种状况都可能发生，这才是辩论的魅力。

### 提示词装配规则

```
System:
  你是{角色名}，{soul}。{rule}
  
  你现在参加一场辩论赛。
  辩题：{topic}
  背景：{background}
  你的立场：{正方/反方}
  你的位置：{一辩/二辩/三辩/四辩}
  
  {阶段提示词}
  
  输出纯文本发言即可，不要解释你的思考过程。

User:
  以下是截至目前本场辩论的全部记录：
  ---
  {全文辩论记录，每条格式：[正方/反方][位置]：{content}}
  ---
  
  当前环节：{round_name}
  这是整场辩论的第 {round_index} 轮发言。
  {立论/驳论/总结：本环节建议输出约 600~700 / 300~400 / 600~700 tokens 的内容}
  {对辩/自由辩论：
    我方已使用 {my_used} tokens（共 {my_total}），对方已使用 {opponent_used} tokens（共 {opponent_total}）
    （本次最多可输出 {my_remaining + 80} tokens，累计达到 {my_total} tokens 后我方失去发言权）}
  
  轮到你发言了：
```

### 阶段提示词

#### 立论陈词（正方一辩）

```
现在是你方立论环节。作为正方开篇，为本场辩论定下基调。篇幅建议 600~700 tokens 之间。
```

#### 立论陈词（反方一辩）

```
现在是你方立论环节。作为反方开篇，建立本方论证框架。篇幅建议 600~700 tokens 之间。
```

#### 驳论（反方二辩）

```
现在是驳论环节，你的任务是反驳正方立论、加固本方立场。篇幅建议 300~400 tokens 之间。
```

#### 驳论（正方二辩）

```
现在是驳论环节，你的任务是反驳反方立论、修复和巩固本方立场。篇幅建议 300~400 tokens 之间。
```

#### 对辩（正方三辩）

```
现在进入对辩环节，你和反方三辩多轮交替发言。留意上方的 token 配额——你方还剩多少、对方还剩多少，都是重要信息。建议单次控制在 80 tokens 以内，一句有力的质问或回应往往比长篇大论更有效，但不强制。
如果你方 token 用完，本轮失去发言权；如果对方 token 先用完，你方依然可以继续输出直到自己也耗尽——可以一次打完所有剩余 token，也可以继续保持多轮短促输出。
```

#### 对辩（反方三辩）

```
现在进入对辩环节，你和正方三辩多轮交替发言。留意上方的 token 配额——你方还剩多少、对方还剩多少，都是重要信息。建议单次控制在 80 tokens 以内，一句有力的质问或回应往往比长篇大论更有效，但不强制。
如果你方 token 用完，本轮失去发言权；如果对方 token 先用完，你方依然可以继续输出直到自己也耗尽——可以一次打完所有剩余 token，也可以继续保持多轮短促输出。
```

#### 总结陈词（反方四辩）

```
现在是总结陈词环节，你是反方收尾。回顾全场，指出正方始终未能解决的问题，升华本方立场。篇幅建议 600~700 tokens 之间。
```

#### 总结陈词（正方四辩）

```
现在是总结陈词环节，你是正方收尾。回顾全场，指出反方始终未能有效回击的核心论点，升华本方立场。篇幅建议 600~700 tokens 之间。
```

#### 自由辩论（所有辩手共用）

```
现在是自由辩论环节，双方交替发言，节奏紧凑。每次随机选派一名辩手出场，现在轮到你。

留意上方的 token 配额——你方还剩多少、对方还剩多少，都是重要信息。建议单次控制在 80 tokens 以内，一句有力的质问或回应往往比长篇大论更有效，但不强制。
如果你方 token 用完，本轮失去发言权；如果对方 token 先用完，你方依然可以继续输出直到自己也耗尽——可以一次打完所有剩余 token，也可以继续保持多轮短促输出。
```

#### 裁判

```
你是本场辩论赛的裁判，请根据整场辩论记录进行评判。

评分维度（满分 10 分）：
- 内容与论据（权重 30%）：论据充分度、事实准确性
- 逻辑与推理（权重 25%）：论证严密性、逻辑自洽性
- 表达与语言（权重 20%）：语言流畅度、说服力
- 反驳与应变（权重 25%）：反驳精准度、抓对方漏洞能力

加权总分 = content×0.30 + logic×0.25 + expression×0.20 + rebuttal×0.25

输出严格 JSON：
{
  "scores": [
    { "side": "pro/con", "position": 1-4, "content": 1-10, "logic": 1-10, "expression": 1-10, "rebuttal": 1-10, "comment": "评语" }
  ],
  "winner": "pro/con",
  "bestPro": 1-4,
  "bestCon": 1-4,
  "overallBest": 1-4,
  "summary": "总体评价"
}
```

              ▼                ▼                 ▼

#### 空闲态

- 中央醒目位置显示「开始新辩论」按钮
- 下方列出历史辩论记录（按时间倒序），每项显示：辩题、日期、状态（已结束/进行中）、胜负结果
- 点击历史记录进入回放态（只读查看）

#### 设置弹窗（DebateSetupModal）

点击「开始新辩论」弹出设置界面：

- **辩题**：输入框
- **背景资料**：textarea，可选
- **正方一~四辩**：从角色列表下拉选择（可重复选择同一角色）
- **反方一~四辩**：从角色列表下拉选择（可重复选择同一角色）
- **裁判**：从角色列表选择
- 「开始辩论」按钮

校验：所有 9 个位置必须填满，只显示绑定了 `type="chat"` 大脑的角色。

### 侧边栏

side 模式为 debate 时，侧边栏显示该角色名下的历史辩论列表（同 Agent 的 session 列表逻辑）。

## 技术架构

### 通信流程

```
DebateSetupModal → IPC: debate:start → 主进程 debate handler
                                          │
                                    按轮次依次调用 LLM
                                    每轮完成后发 IPC 推送到前端
                                          │
前端 DebateView ← IPC: debate:progress ←──┤
    实时显示      ← IPC: debate:message ←──┤ 每句发言
                  ← IPC: debate:done    ←──┤ 辩论结束含评分结果
                  ← IPC: debate:error   ←──┤ 异常
```

### IPC 通道

| 通道 | 方向 | 说明 |
|------|------|------|
| `debate:start` | 渲染→主进程 | 启动辩论 |
| `debate:stop` | 渲染→主进程 | 中止辩论 |
| `debate:progress` | 主进程→渲染 | 当前阶段/发言者信息 |
| `debate:message` | 主进程→渲染 | 单条发言内容（SSE 流式） |
| `debate:done` | 主进程→渲染 | 辩论结束（含评分结果） |
| `debate:error` | 主进程→渲染 | 异常通知 |
| `debate:list` | 渲染→主进程 | 历史辩论列表 |
| `debate:get` | 渲染→主进程 | 单场完整记录 |

### 辩论编排逻辑（主进程 handler）

```
startDebate(params):
  1. 创建辩论数据，初始化各队 token 配额
  2. 遍历 Round 1-5
     for each round:
       for each speaker in round:
         - 从 DB 加载该角色 brain+role 信息
         - 拼 system prompt = 角色 soul+rule + 辩位提示词 + 辩论规则
         - 拼 user message = 全部辩论记录
           （对辩/自由辩论附加双方已使用 token 配额）
         - 调用 LLM（流式），max_tokens = 该方剩余配额 + 80（缓冲）
         - 推流到前端，保存 DebateMessage
         - 扣除该方已消耗 token
         - token 耗尽时切换逻辑见对应阶段规则
  3. 辩论结束 → 调裁判 LLM
     - 拼裁判 system prompt + 全部辩论记录
     - 裁判 LLM 输出 JSON 评分
     - 保存 DebateScore + DebateResult
     - 推 debate:done
```

### LLM 调用方式（流式）

与 Chat 的流式实现一致，复用已有的流式 IPC 机制。每条发言在前端逐字渲染，效果同 Chat 消息。

- 每次调用是独立的（没有多轮对话的累积上下文）
- 上下文 = system prompt + 全部历史发言
- `stream: true`，通过 `debate:message` 通道逐 chunk 推流
- max_tokens 设置：

| 环节 | max_tokens | 策略 |
|------|-----------|------|
| 立论/总结 | 780 | system prompt 提示 600~700 区间，max_tokens=780（预算+80 余量） |
| 驳论 | 480 | system prompt 提示 300~400 区间，max_tokens=480（预算+80 余量） |
| 对辩 | 剩余配额 + 80 | system prompt 建议 80 以内，暴露双方剩余配额，LLM 自行决策 |
| 自由辩论 | 剩余配额 + 80 | system prompt 建议 80 以内，暴露双方剩余配额，LLM 自行决策 |
| 裁判 | 2048 | 输出完整 JSON 评分 |
