# 辩论赛功能（Debate）

## 产品定位

一个 LLM 编排的辩论赛沙盒。选 8 个辩手角色（各绑定一个 chat 类型大脑）+ 1 个裁判大脑，系统从 9 个裁判人格中随机抽取 3 个，输入辩题和背景，系统按辩论赛规则依次驱动各辩位发言，最终由 3 位裁判独立打分并聚合判定胜负。

**本质是 LLM 编排，不是 Agent** — 没有工具调用，没有 ReAct 循环。只是按规则依次调 LLM，喂入全部上下文，输出当前环节的发言。

---

## 辩论流程

采用标准辩论赛格式，分为五个阶段加裁判评判。与 Chat/Agent 不同，辩论流程是**手动步进式**——每点一次「下一步」按钮，系统执行一轮发言（构建 prompt → 调 LLM → 流式输出 → 保存），然后等待用户点击下一次。这意味着：

- 用户可以看完本轮输出后，再决定是否继续
- 调试模式下可在本轮完成后查看完整的 prompt 内容（含战术分析 prompt）
- 随时可以停下来分析当前局势

```
用户点击「下一步」
  ↓
后端获取当前发言者（状态机：getNextSpeaker）
  ↓
构建 system prompt（角色 soul + rule + 辩位提示词）+ user message（全部辩论记录）
  ↓
（对辩/自由辩论）先执行一轮战术分析 LLM 调用，分析结果注入 user message
  ↓
（调试模式）将 system + user（含战术分析）通过 debate:prompt 推送给前端
  ↓
调用 LLM（流式），通过 debate:delta 逐 chunk 推送到前端
  ↓
前端实时渲染发言内容（debate:delta）
  ↓
保存 DebateMessage 到数据库
  ↓
发送 debate:round_done 信号，按钮恢复可点击
  ↓
等待用户再次点击「下一步」
```

### 五阶段轮次定义

```
Round 1 ─ 立论陈词（预算 500 字 ≈ 2'30"）
  正方一辩 → 反方一辩
  system prompt 提示 400~500 字区间
  max_tokens=4096 安全阀

Round 2 ─ 驳论阶段（预算 300 字 ≈ 1'30"）
  反方二辩 → 正方二辩
  system prompt 提示 200~300 字区间
  max_tokens=4096 安全阀

Round 3 ─ 对辩阶段（多轮交锋，预算 300 字/方）
  正方三辩 ↔ 反方三辩 交替
  system prompt 建议单次 30~80 字（不强制）
  暴露双方剩余字数配额
  一方耗尽 → 对方继续直到自己也耗尽 → 双方都耗尽结束
  max_tokens=null（由字数预算控制，安全阀由 streamSpeech 内置）

Round 4 ─ 自由辩论（多轮交锋，预算 800 字/方）
  正方先，双方交替
  每次从该方 4 人中加权随机选（三辩 50%，其余 3 人各 ~16.7%）
  system prompt 建议单次 30~80 字（不强制）
  暴露双方剩余字数配额
  一方耗尽 → 对方继续直到自己也耗尽 → 双方都耗尽结束
  max_tokens=null（由字数预算控制）

Round 5 ─ 总结陈词（预算 500 字 ≈ 2'30"）
  反方四辩 → 正方四辩
  system prompt 提示 400~500 字区间
  max_tokens=4096 安全阀

裁判评判（3 次点击，每次一个裁判）
  详见下方「裁判系统」章节
  max_tokens=8192
```

## 裁判系统

### 裁判人格系统

系统内置 9 个裁判人格，每次辩论创建时从池中无放回随机抽取 3 个。人格差异体现在**权重矩阵**上——所有裁判共享 4 个评分维度，但各维度的重视程度不同。权重总和恒为 1.0。

| # | 人格名称 | prompt_soul | 内容权重 | 逻辑权重 | 表达权重 | 反驳权重 |
|---|---------|------------|---------|---------|---------|---------|
| 1 | 严谨学者 | 以逻辑严密著称，论证漏洞不可原谅，对语言风格不太在意 | 0.25 | 0.45 | 0.05 | 0.25 |
| 2 | 修辞大师 | 语言艺术鉴赏家，更看重表达的说服力和感染力 | 0.20 | 0.15 | 0.50 | 0.15 |
| 3 | 战术分析师 | 专注辩论中的攻防转换，谁能有效反驳谁就得高分 | 0.15 | 0.25 | 0.10 | 0.50 |
| 4 | 中立主义者 | 公正均衡，不偏重任何单一维度 | 0.30 | 0.25 | 0.20 | 0.25 |
| 5 | 事实核查官 | 只信事实和证据，数据不准确不可原谅 | 0.55 | 0.25 | 0.05 | 0.15 |
| 6 | 即兴艺术家 | 欣赏临场发挥和创新角度 | 0.15 | 0.15 | 0.35 | 0.35 |
| 7 | 传统守护者 | 看重立论框架完整性和总结升华能力 | 0.35 | 0.30 | 0.25 | 0.10 |
| 8 | 激进辩手 | 偏好攻击性，强有力的反驳比温和论述更有价值 | 0.10 | 0.20 | 0.15 | 0.55 |
| 9 | 温和评判 | 包容态度，关注整体质量和建设性对话 | 0.25 | 0.20 | 0.30 | 0.25 |

LLM 只输出原始分（0-10 整数），加权总分由**程序**根据当前裁判人格的权重矩阵计算：

```
weightedTotal = content × w.content + logic × w.logic + expression × w.expression + rebuttal × w.rebuttal
```

### 裁判评判流程（分两步，共 4 次用户点击）

**Phase 1 — 打分阶段（用户连续点击 3 次「下一步」，每次运行一个裁判）：**

```
第 1 次点击 → executeOneJudge(state, judgeIndex=0):
  发送 isFirst delta → 前端立即显示裁判姓名 + 动画点 + 闪烁光标
  调用 LLM（人格 system prompt + 辩论记录 + 评分规则）→ 解析 JSON → parseInt 校验
  程序按人格权重计算每位辩手的加权总分
  写入 DebateScore（8 条记录）
  构建 markdown 评分表格 → 一次性发送给前端（debate:delta + isFirst=false）
  保存 DebateMessage 到 DB
  state.judgeIndex++（从 0 变为 1）
  发送 round_done → 按钮变为「下一步」
  （不是最后一个裁判 → 不发送 judging_done）

第 2 次点击 → executeOneJudge(state, judgeIndex=1):
  同上流程，第二个裁判
  state.judgeIndex++（从 1 变为 2）
  发送 round_done → 按钮变为「下一步」

第 3 次点击 → executeOneJudge(state, judgeIndex=2):
  同上流程，第三个裁判
  state.judgeIndex++（从 2 变为 3）
  发送 round_done + judging_done → 按钮变为「查看结果」
```

**Phase 2 — 决出胜负（用户点击「查看结果」，触发 aggregateJudging）：**

```
Step 1 - 计算每个辩手最终分：
  从 DebateScore 读取所有 weightedTotal（不为 null）
  按 side-position 分组（如 "pro-1", "con-3"）—— 注意不是按 roleId 分组，
    因为同一角色可能出现在多个辩位上
  每个分组的最终分 = 该组所有 weightedTotal 的平均值

Step 2 - 判定胜负：
  正方总分 = Σ 正方 4 个分组的最终分
  反方总分 = Σ 反方 4 个分组的最终分
  winner = 总分高的一方（proSum >= conSum 则正方胜）

Step 3 - 最佳辩手：
  全场最佳 = 最终分最高的辩手（position）
  正方最佳 = 正方最终分最高的辩手
  反方最佳 = 反方最终分最高的辩手

输出：
  写入 DebateResult（unique on debateId，单次执行）
  更新 Debate.status = 'completed'
  state.completed = true
  返回 { winner, bestPro, bestCon, overallBest, proTotal, conTotal }
```

### 裁判 LLM 调用细节

```
System Prompt:
  你是本场辩论赛的裁判，{persona.name}。
  {persona.promptSoul}

User Message:
  以下是本场辩论的完整记录：
  ---
  [正方一辩]：...
  [反方一辩]：...
  ...

  {JUDGE_SCORING_RULES}
  请根据你对 {persona.name} 的角色定位给出评分：
```

评分规则（在 user message 中，不在 system prompt）：

```
评分维度（满分 10 分，整数）：
- 内容与论据（content）：论据充分度、事实准确性
- 逻辑与推理（logic）：论证严密性、逻辑自洽性
- 表达与语言（expression）：语言流畅度、说服力
- 反驳与应变（rebuttal）：反驳精准度、抓对方漏洞能力

评分参考标准：
- 8-10 分：出色，远超预期
- 6-7 分：良好，达到预期
- 4-5 分：一般，有改进空间
- 1-3 分：差，明显不足

输出严格 JSON 数组（每个辩手一个元素），不要包含任何其他内容：

[
  { "side": "pro/con", "position": 1-4, "content": 0-10, "logic": 0-10, "expression": 0-10, "rebuttal": 0-10, "comment": "约 200 字的点评" },
  ...
]
```

注意事项：
- `max_tokens = 8192`（非 2048——JSON 评分数组 + 点评需要更大输出空间）
- LLM 输出后程序做 `parseInt` 校验，防止 NaN 污染数据库
- 每轮裁判的 8 条 DebateScore 数据独立写入

## 提示词系统

### 设计原则

**阶段提示词只做两件事**：告诉 LLM 当前是什么环节、目标是帮团队赢下比赛。不给结构要求、不给写作建议、不限制篇幅。角色灵魂由 soul+rule 决定，环节信息只负责让 LLM 知道「该说什么环节的话」。

**对辩和自由辩论暴露双方剩余字数配额**，让 LLM 自己战略决策用多少。甚至可以选择在对方耗尽后连续输出扩大优势。

### 提示词装配规则

```
System:
  你是{角色名}，{soul}。{rule}

  你现在参加一场辩论赛。
  正方辩题：{proTopic}
  反方辩题：{conTopic}
  背景：{background}

  你的立场：{正方/反方}（{己方辩题}）
  你的位置：{一辩/二辩/三辩/四辩}

  你的唯一目标是在这场辩论中获胜。尽一切努力说服裁判和观众——用最强有力的论据、最严密的逻辑，抓住对方每一个漏洞。

  {阶段提示词}

  输出纯文本发言即可，不要解释你的思考过程。

User:
  以下是截至目前本场辩论的全部记录：
  ---
  {全文辩论记录，每条格式：[正方/反方][位置]：{content}}
  ---

  当前环节：{label}
  这是整场辩论的第 {roundIdx} 轮发言。
  {立论/驳论/总结：本环节建议输出约 {lo}~{budget} 字的内容。}
  {对辩/自由辩论：
    我方已使用 {myUsed} 字（共 {budget}），对方已使用 {oppUsed} 字（共 {budget}）
    （我方剩余 {myRemaining} 字，累计达到 {budget} 字后我方失去发言权）}

  重申立场：{正方/反方} —— {己方辩题}

  {对辩/自由辩论且有战术分析时，在"轮到你发言了"之前注入：
    战术分析：
    {analysisText}
  }

  轮到你发言了：
```

### 阶段提示词

#### 立论陈词（正方一辩 / 反方一辩）

- **正方**：`现在是你方立论环节。作为正方开篇，为本场辩论定下基调。篇幅建议 400~500 字之间。`
- **反方**：`现在是你方立论环节。作为反方开篇，建立本方论证框架。此时无需深入反驳正方一辩的发言，驳论环节会专门处理。篇幅建议 400~500 字之间。`

#### 驳论（反方二辩 / 正方二辩）

- **反方**：`现在是驳论环节，你的任务是反驳正方立论、加固本方立场。篇幅建议 200~300 字之间。`
- **正方**：`现在是驳论环节，你的任务是反驳反方立论、修复和巩固本方立场。篇幅建议 200~300 字之间。`

#### 对辩（三辩共用）

```
现在进入对辩环节，你和对方三辩多轮交替发言。留意上方的字数配额——你方还剩多少、对方还剩多少，都是重要信息。
如果你方字数用完，本轮失去发言权；如果对方字数先用完，你方依然可以继续输出直到自己也耗尽——可以一次打完所有剩余字数，也可以继续保持多轮短促输出。
```

#### 自由辩论（所有辩手共用）

```
现在是自由辩论环节，双方交替发言，节奏紧凑。每次随机选派一名辩手出场，现在轮到你。

留意上方的字数配额——你方还剩多少、对方还剩多少，都是重要信息。
如果你方字数用完，本轮失去发言权；如果对方字数先用完，你方依然可以继续输出直到自己也耗尽——可以一次打完所有剩余字数，也可以继续保持多轮短促输出。
```

#### 总结陈词（反方四辩 / 正方四辩）

- **反方**：`现在是总结陈词环节，你是反方收尾。回顾全场，指出正方始终未能解决的问题，升华本方立场。篇幅建议 400~500 字之间。`
- **正方**：`现在是总结陈词环节，你是正方收尾。回顾全场，指出反方始终未能有效回击的核心论点，升华本方立场。篇幅建议 400~500 字之间。`

### 战术分析机制（对辩/自由辩论专用）

对辩和自由辩论阶段，每次发言前先执行一轮战术分析 LLM 调用：

```
System:
  你是辩论赛的{正方/反方}{位置}，你的立场是：{side} —— {topic}
  你的目标是赢下这场比赛。分析当前局势，为你的下一轮发言制定策略。

User:
  辩题：正方「{proTopic}」vs 反方「{conTopic}」
  以下是截至目前本场辩论的全部记录：
  ---
  {全部历史}
  ---

  当前环节：{label}
  双方字数：我方 {myUsed}/{budget}，对方 {oppUsed}/{budget}

  评估以下维度：
  1. 致命漏洞：对方尚未被有效反驳的逻辑漏洞或事实错误
  2. 防守回应：对方正在攻击我方且尚未有效回应的点
  3. 新攻击角度：尚未展开、但能有力支撑己方立场的新角度

  输出两项内容：

  策略一：从 1~3 中选当前最重要的一个方向，一句话说明。
  新角度参考（用于后续轮次）：基于维度 3，给一个尚未使用的新攻击角度作为种子。
```

战术分析结果注入到主 user message 的「轮到你发言了」之前。`max_tokens=4096`，`stream=false`（不推送到前端渲染，仅在调试模式可见）。

## 存储方案

采用 **SQLite/Prisma** 存储全部辩论数据，不使用 Markdown 或 JSONL。辩论赛数据需要被搜索（按辩题、角色、时间）、回放、统计，关系型数据库是自然选择——Markdown 归档和 JSONL 都是文件级存储，不支持关系查询和联表。

### 数据模型

```prisma
model Debate {
  id              String    @id @default(uuid())
  proTopic        String    // 正方辩题
  conTopic        String    // 反方辩题
  background      String?   // 背景资料
  debugMode       Boolean   @default(false) // 调试模式，持久化到 DB
  summary         String?   // 保留字段（暂未使用），计划用于搜索摘要
  judgePersonas   String?   // JSON 数组，如 "[1,3,7]"，本场选中的 3 个裁判人格 id
  status          String    @default("ongoing") // "ongoing" | "completed"
  createdAt       DateTime  @default(now())
  updatedAt       DateTime  @updatedAt

  positions   DebatePosition[]
  messages    DebateMessage[]
  scores      DebateScore[]
  result      DebateResult?
}

model DebatePosition {
  id        String @id @default(uuid())
  debateId  String
  roleId    String // FK → Role.id
  side      String // "pro" | "con" | "judge"
  position  Int    // 1-4（judge 为 0）
  brainId   String // 冗余存储，方便查询

  debate    Debate @relation(fields: [debateId], references: [id], onDelete: Cascade)

  @@index([roleId])
  @@index([debateId])
}

model DebateMessage {
  id          String   @id @default(uuid())
  debateId    String
  roleId      String   // 发言者 roleId
  side        String   // "pro" | "con" | "judge"
  position    Int      // 1-4（judge 为 0）
  round       String   // "opening" | "rebuttal" | "cross" | "free" | "closing" | "judging"
  content     String   // 发言内容
  tokenCount  Int?     // API 返回的 token 数（仅供参考，编排逻辑已改用字数）
  charCount   Int?     // 发言的实际字数（用于编排判定）
  roundIndex  Int      // 全场第几轮发言
  createdAt   DateTime @default(now())

  debate      Debate   @relation(fields: [debateId], references: [id], onDelete: Cascade)

  @@index([debateId, createdAt])
}

model DebateScore {
  id              String   @id @default(uuid())
  debateId        String
  roleId          String   // 辩手 roleId
  judgeRoleId     String?  // 评分裁判 roleId
  judgePersonaId  Int?     // 裁判人格编号 1-9
  side            String   // "pro" | "con"
  position        Int      // 1-4
  scoreContent    Int?     // 内容/论据 原始分 0-10
  scoreLogic      Int?     // 逻辑/推理 原始分 0-10
  scoreExpression Int?     // 表达/语言 原始分 0-10
  scoreRebuttal   Int?     // 反驳/应变 原始分 0-10
  totalScore      Float?   // 保留字段（旧系统的加权总分，向后兼容）
  weightedTotal   Float?   // 程序按裁判人格权重计算的加权总分
  judgeComment    String?  // 裁判评语
  createdAt       DateTime @default(now())

  debate          Debate   @relation(fields: [debateId], references: [id], onDelete: Cascade)

  @@index([debateId])
  @@index([judgeRoleId])
}

model DebateResult {
  id              String   @id @default(uuid())
  debateId        String   @unique
  winner          String   // "pro" | "con"
  bestPro         Int?     // 正方最佳辩手 position
  bestCon         Int?     // 反方最佳辩手 position
  overallBest     Int?     // 全场最佳辩手 position
  proTotalScore   Float?   // 正方总分
  conTotalScore   Float?   // 反方总分
  judgeIds        String?  // JSON 数组，参与的裁判人格 id 列表
  judgeSummary    String?  // 保留字段，计划用于裁判总结拼接
  createdAt       DateTime @default(now())

  debate          Debate   @relation(fields: [debateId], references: [id], onDelete: Cascade)
}
```

### 数据量估算

一场完整的 5 轮辩论 + 3 裁判：
- Debate: 1 条
- DebatePosition: 9 条（8 辩手 + 1 裁判）
- DebateMessage: ~20~60 条（取决于对辩/自由辩论轮次）
- DebateScore: 24 条（8 辩手 × 3 裁判）
- DebateResult: 1 条

## 状态机与编排逻辑

### 主进程状态（内存中）

```javascript
{
  debateId, proTopic, conTopic, background,
  proRoles: [{ roleId, position: 1-4 }],      // 正方 4 个辩位
  conRoles: [{ roleId, position: 1-4 }],      // 反方 4 个辩位
  judgeRoleId,                                  // 裁判大脑 ID
  judgePersonas: [{ id, name, weights, promptSoul }], // 本场选中的 3 个人格
  roleCache: Map<roleId, { name, brain }>,      // 角色 + 大脑缓存
  allMsgs: [{ side, position, content, phase }], // 全部历史发言
  roundIdx,                                      // 当前轮次编号
  perSideChars: { pro: 0, con: 0 },              // 当前阶段各字数
  phaseIndex: 0-5,                               // 当前阶段索引
  phaseStepIndex,                                 // 固定发言列表中的步进
  crossTurn: 'pro' | 'con',                      // 对辩轮到谁
  freeTurn: 'pro' | 'con',                       // 自由辩论轮到谁
  debugMode, completed, judgeIndex: 0-3,         // 裁判进度
}
```

### 阶段状态机（getNextSpeaker）

```
while (phaseIndex < ROUNDS.length):
  round = ROUNDS[phaseIndex]

  if (speakerList):        // 立论/驳论/总结
    if (phaseStepIndex < speakerList.length) → 返回当前发言人, phaseStepIndex++
    else → phaseIndex++, 重置 perSideChars, continue

  if (speakers === 'cross'):  // 对辩
    if (双方都耗尽) → phaseIndex++, 重置, continue
    优先当前 turn 方（有剩余字数）→ 返回三辩, 切换 turn

  if (speakers === 'free'):   // 自由辩论
    if (双方都耗尽) → phaseIndex++, 重置, continue
    优先当前 turn 方（有剩余字数）→ pickFreeDebater（三辩 50%）, 切换 turn

  // 所有阶段完成 → 进入裁判评判
  return { phase: 'judging', judgeIndex, label: '裁判评判' }
```

### 裁判评判触发

`getNextSpeaker` 返回 `{ phase: 'judging', judgeIndex: state.judgeIndex }` 时，`debate:step` handler 调用 `executeOneJudge(event, state, judgeIndex)` 而非 `executeSpeech`。

`executeOneJudge` 内部：
1. 发送 `isFirst` delta → 前端显示裁判名 + 动画
2. 调用 LLM（stream，onDelta 为空）
3. 解析 JSON + parseInt 校验
4. 计算加权总分
5. 写入 8 条 DebateScore
6. 构建 markdown 表格 → 单次 delta 发送
7. 写入 DebateMessage
8. `state.judgeIndex++`
9. 发送 `round_done`（含 personaIndex）
10. 若最后一个裁判，发送 `judging_done`

### 中断恢复（debate:resume）

恢复流程：

1. 从 DB 加载 Debate（含 positions, messages）
2. 恢复 roleCache（重新查询角色 + 大脑）
3. 恢复 judgePersonas（从 debate.judgePersonas JSON 解析）
4. 调用 `recoverPhaseState(debate.messages)` 确定当前阶段：
   - 遍历 ROUNDS，按 round 字段过滤消息
   - 计算各 side 字数消耗，判断阶段是否完成
   - 返回 { phaseIndex, phaseStepIndex, perSideChars, crossTurn, freeTurn }
5. 查询 DebateScore 的 distinct judgePersonaId，设置 `judgeIndex`
6. 构造 state 对象，注册到 active Map

## 技术架构

### 通信流程

```
DebateSetupModal → IPC invoke: debate:create → 主进程创建辩论，返回 debateId
                                        ↓
用户点击「下一步」→ IPC send: debate:step → 主进程执行一轮发言
                                          │
                                    状态机取发言者
                                    构建 prompt
                                    调用 LLM（流式）
                                          │
前端 ← IPC 通道 ──────────────────────────┤
  debate:delta  ← 流式逐 chunk 推送
  debate:prompt ← 调试模式完整 prompt
  debate:round_done ← 单轮发言完成
  debate:judging_done ← 全部裁判完成
  debate:error ← 异常

用户点击「查看结果」→ IPC invoke: debate:aggregate → 聚合评分，返回结果
```

### IPC 合约一览

| 通道 | 方向 | 类型 | 说明 |
|------|------|------|------|
| `debate:create` | 前端→后端 | invoke/handle | 创建辩论 + 随机选 3 裁判人格 |
| `debate:resume` | 前端→后端 | invoke/handle | 恢复未完成辩论 |
| `debate:step` | 前端→后端 | send/on | 执行一轮发言/一个裁判 |
| `debate:aggregate` | 前端→后端 | invoke/handle | 聚合评分定胜负 |
| `debate:stop` | 前端→后端 | send/on | 中止辩论 |
| `debate:list` | 前端→后端 | invoke/handle | 列出历史辩论 |
| `debate:get` | 前端→后端 | invoke/handle | 获取辩论完整数据 |
| `debate:delta` | 后端→前端 | send/on | 流式发言内容 |
| `debate:prompt` | 后端→前端 | send/on | 调试模式推送 prompt |
| `debate:round_done` | 后端→前端 | send/on | 单轮完成信号 |
| `debate:judging_done` | 后端→前端 | send/on | 裁判全部完成信号 |
| `debate:done` | 后端→前端 | send/on | 辩论结束信号 |
| `debate:error` | 后端→前端 | send/on | 错误信号 |

### LLM 调用方式

与 Chat 的流式实现一致，复用 `streamSpeech` 函数（`main/handlers/debate.js`）：

- 基于 SSE（Server-Sent Events），逐 chunk 解析 `data: {...}` 行
- 通过 `onDelta` 回调逐字发送到前端
- `max_tokens` 设置：

| 环节 | max_tokens | 策略 |
|------|-----------|------|
| 立论/总结 | 4096 | 安全阀，由字数预算（500 字）控制实际长度 |
| 驳论 | 4096 | 安全阀，由字数预算（300 字）控制实际长度 |
| 对辩 | null | 由字数预算控制，不设 token 上限 |
| 自由辩论 | null | 由字数预算控制，不设 token 上限 |
| 战术分析（预调用） | 4096 | 分析输出较短，安全阀 |
| 裁判 | 8192 | 输出 8 个辩手的 JSON 评分数组 + 点评，需要较大空间 |

### 对辩字数计时

```
CROSS_CHARS_PER_SIDE = 300  // 每方可用字数预算

每次 API 调用 max_tokens=null（放开），由字数预算控制轮次
每方累计字数 = Σ 该方每次发言的 content.length
当一方累计字数 ≥ 300 → 该方失去发言权
对方继续使用剩余字数 → 双方都耗尽 → 对辩结束
```

### 自由辩论字数计时

```
FREE_DEBATE_CHARS_PER_SIDE = 800  // 每方可用字数预算

每次 API 调用 max_tokens=null，由字数预算控制
每方累计字数 = Σ 该方每次发言的 content.length
当一方累计字数 ≥ 800 → 该方失去发言权
对方继续 → 双方都耗尽 → 自由辩论结束
```
